# V1.6 / 缺陷对照审计（2026-09-17）

本报告是对 V1.6 开发就绪基线、`缺陷.markdown` 与当前后端/前端运行模板的静态对照。没有在本次审计中启动容器、执行真实 LDAP/MinIO/ClamAV 联调或运行全量测试，因此“已实现”仅表示代码/自动化测试中可见，不能替代验收证据。Docker 构建、模板物化和测试属于另一个 QA 任务，完成后应把实际命令输出与本报告一起归档。

后续 QA 已完成：见 [2026-09-17 容器验证报告](qa-2026-09-17.md)。后端现有全量测试 83/83、前端 Node 9/9 以及 BOM 浏览器交互回归通过，源码与模板严格比对通过。下表仍反映完整 V1.6 条款的未关闭项，不能用这批回归测试替代真实环境验收。本轮编辑器针对现有 BOM 草稿，尚不包含新建 BOM/升版复制的完整页面流程。

代码加密时以 `runtime_templates` 中将被物化到容器的模板作为运行时证据；源码与模板仍须由同步脚本检查。用户已明确批准企业透明加密/未知加密文件保留密文，并允许授权下载、BOM 绑定和发布；因此“opaque 可下载/绑定/发布”不是缺陷，前提是扫描结果和该处置完整留痕。

## 仍然阻断 V1.6 的实现缺口

* **Revision 级发布屏障尚未完成。** [views.py.tmpl:390-407](../runtime_templates/plm/views.py.tmpl) 创建或取得 `ReleasePublication`、`ReleaseActivation` 和 `ReleasePromotion` 后直接把 promotion 标成 `promoted`、activation 标成 `active`，没有从 quarantine/draft 执行 `CopyObject`、固定 `s3_version_id`、校验对象或整组失败回滚。因此不能证明 V16-13 的“第 3 个 promotion 失败时前 2 个也不可见、retry 不重复”语义。
* **上传协议仍缺少 V1.6 的持久分片回执模型。** `UploadSession` 只有会话级字段（[models.py.tmpl:127-140](../runtime_templates/plm/models.py.tmpl)），没有 `PartUpload`、attempt/generation、每片长度/checksum、`commit_unknown` 状态。`views.py.tmpl:583-593` 返回的是最多 20 个 URL 和空 `signed_headers`；`views.py.tmpl:82-110` 只按 ETag/ListParts 对账。无法形成 V16-06/V16-11 所需的服务端回执、每片 checksum 和 finalize 幂等证明。
* **异步 finalize 幂等和错误映射不完整。** `views.py.tmpl:652-667` 每次请求都可创建新的 `FinalizeJob`，无同一 operation key 的唯一约束，且超过阈值的作业返回后没有明确 `Location`/`Retry-After` 契约。长度错误映射为 `UPLOAD_SIZE_MISMATCH` 而 V16-11 要求稳定的 `UPLOAD_PART_INVALID`；超限创建时返回 400（[views.py.tmpl:573-578](../runtime_templates/plm/views.py.tmpl)），与 V16-05 要求 `413 UPLOAD_SIZE_EXCEEDED` 的边界需补测试和统一响应。
* **扫描服务虽有 ClamAV 调用，但缺少真实门禁证据和完整版本绑定。** `jobs.py.tmpl:35-108` 实现了 INSTREAM、EICAR/异常的 fail-closed 路径，且透明/未知加密按已批准 opaque 路径记录；独立 ClamAV 容器已在 docker-compose.yaml 中配置且本轮健康检查通过；仍缺病毒库更新告警、真实 VersionId/策略版本对账及停机/超时/超 4 GiB 的完整验收证据。`AttachmentVersion.SECURITY_STATES`（[models.py.tmpl:255-271](../runtime_templates/plm/models.py.tmpl)）也没有 `opaque` 选项，代码通过字符串使用该状态，需迁移/枚举一致性检查。V16-12 仍为未验收。
* **BOM 导入绕过结构与不可变校验。** `jobs.py.tmpl:324-340` 使用 `update_or_create` 写 BOM、Revision、Item，不调用 `validate_bom_item/tree`，不检查现有 Revision 状态、位置唯一、替代组/单位维度等；预检只检查根/子 Revision 存在及子件 released（`jobs.py.tmpl:365-374`）。BOM API 编辑端点本身有 If-Match/草稿门禁，但导入形成第二条绕过路径。
* **导入确认令牌未落地。** `views.py.tmpl:691-699` 的 `commit` 只按任务状态调用 worker，没有校验 `confirm_token`、目录版本、操作者角色、TTL 或 stale confirmation。`ImportJob` 模型（[models.py.tmpl:189-196](../runtime_templates/plm/models.py.tmpl)）也没有 confirm token/过期/操作者快照字段。V16-08/V16-09 不能关闭。
* **导出没有真正应用过滤/脱敏范围。** `jobs.py.tmpl:409-421` 对 category/part/BOM 均使用全表查询；`filters` 未用于授权范围裁剪，当前 `_safe_cell` 只解决公式注入，不实现角色字段/行裁剪。V16-08/V16-10 的“无权行与敏感字段不出现”仍缺实现与证据。
* **数据库模型仍缺关键冻结约束。** `PartRevision`、`BOMRevision` 没有 `effective_range`；BOM/BOMRevision 没有 tenant 字段；BOMItem 没有替代组、父项复合外键；AuditEvent（[models.py.tmpl:177-187](../runtime_templates/plm/models.py.tmpl)）没有 `request_id/job_id/prev_hash/entry_hash`，迁移没有 PostgreSQL `tstzrange` 排他约束、发布后不可变触发器或 append-only 数据库权限。现有唯一约束只覆盖 part tenant code、attachment/version、placement key、activation/version（[models.py.tmpl:60-62,269-315](../runtime_templates/plm/models.py.tmpl)）。
* **SoD 降级流程缺失。** Revision/BOM transition 代码有提交人、审核人、发布人的基本互斥检查（如 [views.py.tmpl:375-389](../runtime_templates/plm/views.py.tmpl)），但没有 V1.6 §4.2 的单对象、24 小时、双人批准、工单和完整审计的例外机制，也没有 `NO_ELIGIBLE_ACTOR` 稳定错误码。
* **角色/管理契约仍有双路由和不一致。** 运行模板同时暴露 `/auth/users`、`/admin/users` 和 `/admin/users/{id}`（[urls.py.tmpl:24](../runtime_templates/plm/urls.py.tmpl)）；前端管理页仍主要调用 `/auth/users`。`settings.py.tmpl:14` 在 DRF 默认认证中启用 `BasicAuthentication`，生产要求关闭。`admin_health` 只检查数据库和对象存储（[views.py.tmpl:725-745](../runtime_templates/plm/views.py.tmpl)），没有 LDAP、Redis/Celery、ClamAV、WAL/RPO 或 CORS 状态。
* **API 文档和实际路由尚未收敛。** `docs/openapi.yaml` 声明 `/attachments/upload-sessions/{id}/finalize`、`/attachment-versions/{id}/download` 为 GET/POST 语义及 `attachment_role`、`declared_sha256`；实际路由使用 `/actions`（`finalize` action）、`/complete` 兼容路径和不同字段。OpenAPI 的 `Revision.effective_range`、BomItem alternative 字段、Error envelope 也没有对应模型/统一响应。应在 M0 选择单一规范并做契约测试。
* **附件下载/预览后端有基础实现，但前端没有完整工作流。** `attachment_views.py.tmpl:101-175` 有 mode、nonce、Range、license 和固定 placement 的检查，且 opaque 可用；前端 `part-detail` 仅展示上传控件/说明，没有附件版本列表、扫描状态、三种下载 mode、license/content 请求、过期重试和发布屏障信息。
* **Where-Used 已改为 410，但仍保留路由。** `views.py.tmpl:228-230`、`:272-274` 返回 `NOT_SUPPORTED`，符合稳定拒绝方向；需把它从生产 OpenAPI/导航中移除，并为 410 契约留证，避免被误认为已实现能力。
* **运维脚本是骨架而非演练证据。** `scripts/backup_restore.sh` 只执行加密 `pg_dump`/`pg_restore --list`；`docs/backup-restore-runbook.md` 状态明确为“待演练”。`scripts/perf_baseline.py` 只对一个 health URL 做简单并发请求，不执行 §17 的 50 用户混合场景、上传/扫描/finalize/BOM p95/p99，也不记录固定硬件/数据集哈希。V16-28/V16-29 必须保持未通过直到真实演练和报告签字。
* **M0/M3 证据目录为空缺实测结果。** `docs/acceptance-matrix.md` 只有命令建议和 `artifacts/m0-m3/<timestamp>/` 归档约定，没有签字、分类 CSV SHA-256、MinIO 原始探针、迁移 dry-run 数量、容量基线、RPO/RTO、密钥轮换或故障注入结果。

## 建议关闭顺序

1. 先冻结并迁移数据库：`effective_range`/租户/BOM 复合约束、Audit hash 链、PartUpload/confirm/idempotency/发布 placement 实体；同时收敛 OpenAPI 与实际路由。
2. 用真实容器完成 LDAP、角色/SoD、MinIO 双端点/CORS、ClamAV，并把错误码、`Retry-After`、request/job/audit ID 固定下来。
3. 重做 finalize 与 ReleaseActivation 服务：服务端 ListParts/checksum、异步幂等、S3 promotion、整组 visibility、失败重试和下载授权；让 BOM 导入复用同一结构校验服务。
4. 完成前端 BOM 编辑、附件扫描/发布/下载、任务确认和错误展示，并同步模板后构建。
5. 最后执行并归档 V16-01～30：迁移 dry-run/分类 SHA、LDAP 抓包、MinIO 原始探针、EICAR、发布失败注入、故障门禁、备份恢复、容量压测和浏览器矩阵；没有这些证据不能标记 M0～M3 或生产通过。
